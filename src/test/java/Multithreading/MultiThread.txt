Thread class vs Runnable

Thread    → represents the actual thread of execution
Runnable  → represents the task/work that should be executed


Thread:

class MyThread extends Thread {

    @Override
    public void run() {
        System.out.println("Task running");
    }
}

public class Main {
    public static void main(String[] args) {

        MyThread t1 = new MyThread();

        t1.start();
    }
}

Interface:
class MyTask implements Runnable {

    @Override
    public void run() {
        System.out.println("Task running");
    }
}

| Thread                      | Runnable                       |
| --------------------------- | ------------------------------ |
| Class                       | Interface                      |
| Represents a thread         | Represents a task              |
| Extend `Thread`             | Implement `Runnable`           |
| Override `run()`            | Implement `run()`              |
| Task and thread are coupled | Task and thread are separated  |
| Cannot extend another class | Can still extend another class |
| Less flexible               | More flexible                  |
| Usually not preferred       | Usually preferred              |


| State           | Meaning                                        |
| --------------- | ---------------------------------------------- |
| `NEW`           | Thread created but not started                 |
| `RUNNABLE`      | Ready to run or currently running              |
| `BLOCKED`       | Waiting to acquire a monitor lock              |
| `WAITING`       | Waiting indefinitely for another thread/action |
| `TIMED_WAITING` | Waiting for a specified amount of time         |
| `TERMINATED`    | Execution completed                            |

 volatile:

 In multithreaded code, each thread may cache a variable's value in a CPU register or local cache for performance. So if Thread A updates a variable, Thread B might keep seeing the old, stale value because it never re-reads from main memory.

 What volatile does

 Marking a variable volatile tells the compiler/JVM:

 Always read/write directly from main memory, never from a thread-local cache or register.
 This guarantees visibility — if Thread A writes to a volatile variable, Thread B will immediately see the updated value.

thread-safe Singleton using double-checked locking:

public class Singleton {

    private static volatile Singleton instance;

    private Singleton() {}

    public static Singleton getInstance() {

        if (instance == null) {                 // 1st check
            synchronized (Singleton.class) {

                if (instance == null) {         // 2nd check
                    instance = new Singleton();
                }
            }
        }

        return instance;
    }
}

synchronized
    ↓
Prevents two threads from creating
two Singleton objects concurrently

volatile
    ↓
Provides safe publication / visibility
for threads reading instance outside the lock


The second if is also important. Suppose Thread A and Thread B both pass the first instance == null.
Thread A gets the lock first and creates the object. When Thread B later gets the lock, the second check discovers that A already created it.

Why StringBuffer is thread-safe ?

Look at its source — methods are literally marked synchronized:

java
public synchronized StringBuffer append(String str) {
    super.append(str);
    return this;
}

StringBuilder is NOT -
StringBuilder (introduced in Java 5) has the exact same API as StringBuffer but deliberately drops the synchronized keyword, because:

Most string-building happens in a single thread (e.g., building a query, a log line, a JSON string).
Paying lock-acquisition cost every time was wasteful for that common case.
So StringBuilder trades safety for speed.

package Multithreading;

import java.util.LinkedList;
import java.util.Queue;

public class ThreadTester04 {

    public static void main(String[] args) {

        BlockingQueueWithoutWait queue =
                new BlockingQueueWithoutWait(5);

        Thread producer = new Thread(() -> {
            for (int i = 1; i <= 10; i++) {
                queue.add(i);
                System.out.println("Produced: " + i);
            }
        }, "Producer");

        Thread consumer = new Thread(() -> {
            for (int i = 1; i <= 10; i++) {
                int value = queue.remove();
                System.out.println("Consumed: " + value);
            }
        }, "Consumer");

        producer.start();
        consumer.start();
    }
}

class BlockingQueueWithoutWait {

    private final Queue<Integer> queue;
    private final int capacity;

    public BlockingQueueWithoutWait(int capacity) {
        queue = new LinkedList<>();
        this.capacity = capacity;
    }

    public boolean add(int item) {
        while (true) {
            synchronized (this) {
                if (queue.size() < capacity) {
                    queue.add(item);
                    return true;
                }
            }
        }
    }

    public int remove() {
        while (true) {
            synchronized (this) {
                if (!queue.isEmpty()) {
                    return queue.poll();
                }
            }
        }
    }
}

import java.util.LinkedList;
import java.util.Queue;

public class ThreadTester05 {

    public static void main(String[] args) {

        BlockingQueue queue =
                new BlockingQueue(5);

        Thread producer = new Thread(() -> {
            for (int i = 1; i <= 10; i++) {
                queue.add(i);
                System.out.println(Thread.currentThread().getName() + " produced: " + i);
            }
        }, "Producer");

        Thread consumer = new Thread(() -> {
            for (int i = 1; i <= 10; i++) {
                int value = queue.remove();
                System.out.println(Thread.currentThread().getName() + " consumed: " + value);
            }
        }, "Consumer");

        producer.start();
        consumer.start();
    }
}

class BlockingQueue {

    private final Queue<Integer> queue;
    private final int capacity;

    public BlockingQueue(int capacity) {

        queue = new LinkedList<>();
        this.capacity = capacity;
    }

    public boolean add(int item) {
        synchronized (this) {
            while (queue.size() == capacity) {
                try {
                    System.out.println("Queue full. Producer waiting...");
                    wait();
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                    return false;
                }
            }
            queue.add(item);
            System.out.println("Queue after add: " + queue);
            notifyAll();
            return true;
        }
    }

    public int remove() {
        synchronized (this) {
            while (queue.isEmpty()) {
                try {
                    System.out.println("Queue empty. Consumer waiting...");
                    wait();
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                    return -1;
                }
            }
            int element = queue.poll();
            System.out.println("Queue after remove: " + queue);
            notifyAll();
            return element;
        }
    }
}

1. sleep()
java
Thread.sleep(2000); // pauses current thread for 2 seconds
Static method on Thread — always pauses the currently executing thread, not some other thread object.
Does NOT release any locks it's holding (this trips people up — a thread can sleep() while inside a synchronized block and still hold the monitor).
Throws checked InterruptedException — must be caught or declared.
Goes to TIMED_WAITING state.
java
try {
    Thread.sleep(1000);
} catch (InterruptedException e) {
    Thread.currentThread().interrupt(); // restore interrupt status
}

2. join()
java
Thread t1 = new Thread(() -> doWork());
t1.start();
t1.join(); // main thread waits here until t1 finishes
Called on a thread object, from another thread.
Makes the calling thread wait until the target thread dies (finishes execution).
Common use: main thread waits for worker threads to complete before proceeding (e.g., aggregating results).
Also throws InterruptedException.
Overloads exist: join(long millis) — wait at most that long, then proceed anyway.
java
Thread t1 = new Thread(task1);
Thread t2 = new Thread(task2);
t1.start(); t2.start();
t1.join(); t2.join(); // main waits for both before continuing
System.out.println("Both done");

3. interrupt()
java
t1.interrupt();
Does NOT forcibly stop a thread. It just sets a flag (interrupt status = true) on the target thread — it's a cooperative signal, not a kill switch.
Effect depends on what the thread is doing:
If it's blocked in sleep(), wait(), or join() → it immediately wakes up and throws InterruptedException (and the flag is cleared).
If it's running normal code → nothing happens automatically. The thread must periodically check Thread.currentThread().isInterrupted() and respond (e.g., exit a loop).
java
public void run() {
    while (!Thread.currentThread().isInterrupted()) {
        // do work
    }
    System.out.println("Interrupted, exiting cleanly");
}

4. wait()
java
synchronized (lock) {
    while (!conditionMet) {
        lock.wait();   // releases the lock and pauses here
    }
    // proceed once notified AND condition true
}
Must be called from inside a synchronized block on that object — otherwise throws IllegalMonitorStateException.
Releases the lock it's holding while waiting (this is the key difference from sleep(), which holds the lock).
Thread goes to WAITING state until another thread calls notify()/notifyAll() on the same object.
Always call it in a while loop, not if — guards against spurious wakeups (JVM allowed to wake a thread without a real notify) and re-checks the condition.
5. notify()
java
synchronized (lock) {
    conditionMet = true;
    lock.notify(); // wakes ONE waiting thread, chosen arbitrarily
}
Wakes up one thread waiting on that object's monitor (JVM picks which — undefined/arbitrary).
Must also be called inside a synchronized block on the same object.
Woken thread doesn't run immediately — it has to reacquire the lock first, and only proceeds once it gets it.
6. notifyAll()
java
synchronized (lock) {
    conditionMet = true;
    lock.notifyAll(); // wakes ALL waiting threads
}
Wakes every thread waiting on that monitor. They all then compete to reacquire the lock; only one gets it at a time, others go back to waiting for the lock (not for notify).
Almost always preferred over notify() in real code — with notify(), if the "wrong" thread happens to be picked (e.g., waiting for a different condition on the same lock), you get a missed signal / deadlock-like hang. notifyAll() is safer since every thread re-checks its own condition in the while loop.
The classic producer-consumer example (ties it all together)
java
class Buffer {
    private Queue<Integer> queue = new LinkedList<>();
    private int capacity = 5;

    public synchronized void produce(int value) throws InterruptedException {
        while (queue.size() == capacity) {
            wait(); // buffer full, release lock, wait
        }
        queue.add(value);
        notifyAll(); // wake up any waiting consumers
    }

    public synchronized int consume() throws InterruptedException {
        while (queue.isEmpty()) {
            wait(); // buffer empty, release lock, wait
        }
        int value = queue.poll();
        notifyAll(); // wake up any waiting producers
        return value;
    }
}

1. Spring Boot request handling

In Spring Boot, multithreading appears naturally when your application handles many HTTP requests at the same time.

The basic problem is simple:

User A --> /api/orders
User B --> /api/orders
User C --> /api/orders

Spring Boot does not normally process all three requests one after another on the same thread. The embedded server, such as Tomcat, uses a pool of worker threads.

So if you have:

@RestController
public class OrderController {

    @GetMapping("/orders")
    public String getOrders() {
        return "Orders";
    }
}

and 10 users call /orders, different requests can be processed concurrently by different server threads.

The real problem is

Spring beans such as:

@RestController
@Service
@Repository

are usually singleton beans by default.

That means there is typically one shared instance serving many request threads.

For example:

@RestController
public class CounterController {

    private int count = 0;

    @GetMapping("/count")
    public int count() {
        return ++count;
    }
}

This looks harmless. But imagine two requests arrive together:

Thread-1                  Thread-2

read count = 10           read count = 10
increment -> 11           increment -> 11
write 11                  write 11

Expected:

12

Actual could be:

11

So the problem is:

Singleton Spring Bean
        +
Multiple Request Threads
        +
Mutable Shared State
        =
Race Condition
The preferred solution

In Spring Boot, try to make controllers and services stateless.

Good:

@RestController
public class UserController {

    private final UserService userService;

    public UserController(UserService userService) {
        this.userService = userService;
    }

    @GetMapping("/users/{id}")
    public User getUser(@PathVariable Long id) {
        return userService.findById(id);
    }
}

Notice there is no request-specific data stored in fields like:

private Long currentUserId;
private String currentName;
private int count;

Instead, data stays in local variables:

public User findById(Long id) {

    User user = repository.findById(id).orElseThrow();

    return user;
}

id and user are method-local variables, so each request/thread gets its own execution stack.

Conceptually:

Shared UserService object

       ↑               ↑
       |               |
    Thread-1         Thread-2
       |               |
 id = 10           id = 25
 user = A          user = B

No conflict.

package Multithreading;

public class OddEvenPrinter {

    public static void main(String[] args) {

        NumberPrinter printer = new NumberPrinter(10);

        Thread oddThread = new Thread(
                printer::printOdd, "Odd-Thread"
        );

        Thread evenThread = new Thread(
                printer::printEven, "Even-Thread"
        );

        oddThread.start();
        evenThread.start();
    }
}

class NumberPrinter {

    private int number = 1;
    private final int limit;

    public NumberPrinter(int limit) {
        this.limit = limit;
    }

    public synchronized void printOdd() {

        while (number <= limit) {
            while (number % 2 == 0) {
                try {
                    wait();
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                    return;
                }
            }

            if (number <= limit) {
                System.out.println(Thread.currentThread().getName() + " : " + number);
                number++;
                notifyAll();
            }
        }
    }

    public synchronized void printEven() {

        while (number <= limit) {
            while (number % 2 != 0) {
                try {
                    wait();
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                    return;
                }
            }

            if (number <= limit) {
                System.out.println(Thread.currentThread().getName() + " : " + number);
                number++;
                notifyAll();
            }
        }
    }
}

thread-safe singleton

A basic lazy singleton - not thread safe

Solution 1: synchronized method

Simplest thread-safe solution:

class Singleton {

    private static Singleton instance;

    private Singleton() {
    }

    public static synchronized Singleton getInstance() {

        if (instance == null) {
            instance = new Singleton();
        }

        return instance;
    }
}

Problem with this solution

Every call to:

Singleton.getInstance();

must acquire the lock.

Even after the singleton has already been created.

Suppose instance already exists:

100 threads
     ↓
getInstance()
     ↓
synchronized lock
     ↓
return same instance

The synchronization is unnecessary after initialization.

That leads to the famous:

Solution 2: Double-Checked Locking
class Singleton {

    private static volatile Singleton instance;

    private Singleton() {
    }

    public static Singleton getInstance() {

        if (instance == null) {              // Check 1

            synchronized (Singleton.class) {

                if (instance == null) {      // Check 2

                    instance = new Singleton();
                }
            }
        }

        return instance;
    }
}

There are three important pieces:

volatile
+
first null check
+
synchronized + second null check

Let's understand why each exists.

Why first check?
if (instance == null) {

Once the Singleton exists:

instance != null

threads simply:

getInstance()
     ↓
instance == null? NO
     ↓
return instance

No synchronization.

So after initialization:

Thread-1 ──→ return instance
Thread-2 ──→ return instance
Thread-3 ──→ return instance
Thread-4 ──→ return instance

That's the performance benefit.

Why second check?

This is extremely important.

Imagine instance hasn't been created.

Thread-1:

if (instance == null) {

true.

Thread-2 also:

if (instance == null) {

true.

Both want to enter:

synchronized (Singleton.class)

But only one can.

Thread-1                         Thread-2

instance == null ✓              instance == null ✓

acquire lock                     waiting for lock

new Singleton()
instance = Object-A

release lock
                                 acquire lock

Now what should Thread-2 do?

If we didn't have the second check:

synchronized (Singleton.class) {
    instance = new Singleton();
}

Thread-2 would create another object.

So inside the lock we check again:

if (instance == null) {

Thread-2 now sees:

instance = Object-A

Therefore:

instance == null → false

No second object.

That's why it's called:

Double-Checked Locking

We check twice.

Now the important question: why volatile?

This is a famous interview question.

We have:

private static volatile Singleton instance;

Why isn't this enough?

private static Singleton instance;

Because object creation is conceptually more complicated than it looks.

This:

instance = new Singleton();

can be thought of approximately as:

1. Allocate memory
2. Initialize Singleton object
3. Assign reference to instance

Without the Java Memory Model guarantees needed here, problematic reordering/publication could conceptually expose:

1. Allocate memory
2. Assign reference to instance
3. Initialize object

Then imagine:

Thread-1

allocate memory

instance = reference
          ↑
          |
          | Thread-2 checks here
          |
initialize object

Thread-2 sees:

instance != null

and returns it.

But the object may not yet be safely published as fully initialized.

This is the partially initialized object problem.

volatile solves this publication issue
private static volatile Singleton instance;

volatile provides the necessary visibility and ordering/happens-before guarantees around publication of the reference.

So Thread-2 won't observe the correctly volatile-published reference without the constructor's prior initialization effects being visible as required.

This connects directly to the concepts you've been learning:

synchronized
    ↓
Mutual exclusion

volatile
    ↓
Visibility + ordering

Double-checking
    ↓
Avoid unnecessary locking
Important: volatile alone is NOT enough

Another interview trap.

This is still wrong:

private static volatile Singleton instance;

public static Singleton getInstance() {

    if (instance == null) {
        instance = new Singleton();
    }

    return instance;
}

Why?

Because two threads can still do:

T1                           T2

instance == null             instance == null
      ✓                            ✓

new Singleton()              new Singleton()

volatile does not provide mutual exclusion for this check-then-act sequence.

Remember:

volatile
   ↓
visibility/order

NOT
   ↓
only-one-thread-at-a-time
